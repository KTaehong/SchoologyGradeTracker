BessyV2 · System Architecture

A Flutter grades app on a three-tier cloud backend

Grades are captured keyless on the device, then synced up to an API and stored in a PostgreSQL database — the system of record that powers cross-device sync, grade-change notifications, caregiver access, and admin/support tooling. The client is built today; the backend is what this phase builds.

Client tier Application / API tier Data tier built exists today to build this phase

The user's own data

External · read-only · user-initiated

Keyless: no Schoology API key, no OAuth, no stored password, no automated login. The student supplies their own data — nothing is scraped. Ingestion stays on the device; the results sync up.

Data tier — the database

System of record

PostgreSQL is the authoritative store; grades stay owned by the user (a synced copy, ideally end-to-end encrypted). Object storage and a cache sit alongside it.

Privacy as a constraint, not the whole model: putting grades on a server weakens the old "no server ever sees your grades" guarantee. Keep cloud sync opt-in, prefer end-to-end encryption so the server stores ciphertext, minimize what's stored, and keep the device usable offline from its local cache.
